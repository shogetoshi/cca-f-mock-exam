出題の性格

Domain 2: Applications and Integration 33.1%

Messages API の基本

  • 単一エンドポイント POST /v1/messages にすべてが乗る。必須パラメータは model / max_tokens / messages。
  • API はステートレス。マルチターンでは会話履歴全体を毎回送信する。最初のメッセージは user ロール。
  • レスポンスの content はブロックの配列(text / tool_use / thinking など)。type を確認してからアクセスする。
  • stop_reason の値: end_turn(自然終了)/ tool_use(ツール実行要求)/ max_tokens(上限到達=切り捨ての可能性)/ stop_sequence / pause_turn(サーバーツールの中断、再送で再開)/ refusal(安全上の拒否)。
  • マルチフォーマット入力: 画像は base64 または URL の image ブロック、PDF は document ブロック。テキストブロックより前に置く。

Streaming

  • SSE イベントの順序: message_start → content_block_start → content_block_delta(トークンごと)→ content_block_stop → message_delta(stop_reason と usage を含む)→ message_stop。
  • 大きい max_tokens(目安 16K 超)は HTTP タイムアウト回避のためストリーミング必須。チャット UI のリアルタイム表示にも使う。

Message Batches API(頻出)

  • 50% 割引・最大 24時間処理・レイテンシ SLA なし。夜間レポート、週次監査、大量ドキュメント一括処理など「待てる」ワークロード向け。
  • ブロッキングな用途(マージ前チェック、対話 UI)には不適 — そこは同期 API を使う。
  • custom_id でリクエストとレスポンスを対応付ける。結果は順不同で返るので位置ではなく custom_id でキーする。
  • ステータスを ended までポーリングしてから結果を取得。失敗分は custom_id で特定し、修正して再送(例: コンテキスト超過ならチャンク分割)。
  • Batch 内では複数ターンのツール実行はできない(リクエスト途中でツールを実行して結果を返す往復が不可能)。
  • 大量処理の前にサンプルでプロンプトを調整し、一発成功率を上げてから流すのが定石。

Prompt Caching(頻出)

  • プレフィックス一致。レンダリング順は tools → system → messages。前方の1バイトの変化で後方のキャッシュがすべて無効化される。
  • 安定した内容(システムプロンプト、ツール定義、大きな文書)を先頭に、変動する内容(タイムスタンプ、ユーザー固有の質問)を末尾に置く。
  • cache_control: {"type": "ephemeral"} をブロックに付与。TTL はデフォルト5分、オプションで1時間。
  • コスト: キャッシュ書き込み ≈ 1.25倍、読み取り ≈ 0.1倍(最大約90%削減)。
  • 検証は usage の cache_creation_input_tokens / cache_read_input_tokens。読み取りが常に0なら、システムプロンプト内の datetime.now() のような「サイレント無効化要因」を疑う。
  • マルチターンでは最新ターンの末尾にブレークポイントを置き、会話が伸びるたびに差分だけ課金される(cache checkpointing)。

設計・構成管理

  • Claude はインターフェースごとに指示の解釈経路が異なる(Claude Code / Desktop / claude.ai / API / SDK)。API では system プロンプトが唯一の「開発者の声」。
  • コンテンツ境界: 信頼できる指示と untrusted な入力(ユーザー入力・取得した文書)を XML タグ等で明確に分離する。
  • モデルバージョンのピン留め: 本番ではエイリアスでなく特定バージョンを固定し、アップグレードは eval を通してから。リリース間で挙動が変わりうる(breaking behavior changes)。
  • プロンプトもコードと同様にバージョン管理(prompt versioning)。設定は CLAUDE.md / settings.json / プラグイン依存関係で管理。
  • SDLC への統合: コードレビュー、小規模〜大規模リファクタリング、非同期処理、REST/JSON の基礎はここで問われる。

Domain 5: Model Selection and Optimization 16.8%

LLM の基礎

  • LLM は次トークン予測。出力は非決定的(temperature 0 でも完全一致は保証されない)。
  • トークン: 英語で約 3〜4 文字/トークン。入出力両方が課金対象。コンテキストウィンドウは入力+出力の合計上限。
  • プロンプト技法: zero-shot(例なし)/ single-shot(1例)/ multi-shot(複数例)。例が多いほど形式の一貫性が上がる。

モデル選択(頻出)

モデル特性適する用途
Opus最高性能・高コスト・低速複雑な推論、長時間の自律エージェント、大規模リファクタ、難しいコーディング
Sonnet性能と速度・コストのバランス本番の主力。エージェント、コーディング、大量の実務処理
Haiku最速・最安分類、ルーティング、単純な抽出、レイテンシ最優先のタスク
  • 「品質・レイテンシ・コスト」の3軸トレードオフで選ぶ。コスト削減のために闇雲に最小モデルへ落とすのは誤答の定番(品質要件を無視しているため)。
  • モデルオプション: fast mode(出力を高速化)、extended thinking / adaptive thinking(推論を深める。adaptive はモデルが思考量を自動調整)、effort levels(low/medium/high… — 思考の深さとトークン消費を制御)。
  • 思考が必要な複雑タスク → thinking + effort 高め。単純タスク → thinking なし/effort 低で高速・低コスト。

コスト・トークン管理

  • コスト最適化の主要レバー(順に検討): ① プロンプトキャッシュ ② Batch API(50%オフ)③ 適切なモデルティア ④ effort/max_tokens の調整 ⑤ コンテキストの削減(ツール出力の刈り込み)。
  • count_tokens エンドポイントで事前見積もり。usage フィールドで実測を追跡。
  • キャッシュと Batch は併用可能(バッチ内の共有 system にキャッシュを効かせる)。

Domain 1: Agents and Workflows 14.7%

ワークフロー vs エージェント

  • ワークフロー: コードが制御フローを決める(事前定義の手順・分岐)。予測可能でデバッグしやすい。手順が既知ならこちら。
  • エージェント: モデルが次の行動を判断する(ツール選択・ループ)。手順が事前に決められない曖昧なタスク向け。コスト・エラーリスクは高い。
  • 判断基準: タスクの複雑さ/価値がコストに見合うか/モデルがその種のタスクを遂行できるか/エラーの検出・回復が可能か。1つでも No なら単純な構成に留める。

エージェントループ(最頻出パターン)

  • ライフサイクル: リクエスト送信 → stop_reason を確認 → tool_use ならツール実行 → tool_result を user メッセージとして履歴に追加 → 再送信 → end_turn で終了。
  • assistant 応答(tool_use ブロック含む)を履歴に追加してからツール結果を返す。tool_result の tool_use_id は対応する tool_use の id と一致させる。
  • 並列ツール呼び出し: 1応答に複数の tool_use が来たら、全結果を1つの user メッセージで返す。
  • アンチパターン: 自然言語の「完了しました」をパースして終了判定/一律の反復回数上限を主要な停止機構にする/assistant のテキスト有無で完了判定 — 正解は常に stop_reason ベースの制御。

マルチエージェント(coordinator–subagent)

  • ハブ&スポーク: コーディネータがタスク分解・委譲・結果集約・エラー処理・通信のすべてを仲介する(可観測性と一貫したエラー処理のため)。
  • サブエージェントはコンテキストを継承しない。必要な情報(前段の調査結果、制約、出力形式)はプロンプトに明示的に渡す。
  • 並列実行: コーディネータが1つの応答で複数の Task ツール呼び出しを同時に発行する(ターンをまたがない)。Claude Code では allowedTools に "Task" が必要。
  • コーディネータのタスク分解が狭すぎるとカバレッジ漏れが起きる(例: 「クリエイティブ産業」を視覚芸術だけに分解 → 音楽・文学が欠落)。原因切り分けではまず分解のログを見る。
  • コーディネータへのプロンプトは手順の逐次指定ではなく「目標と品質基準」を与え、適応の余地を残す。
  • fork_session: 共有の分析ベースラインから分岐して複数アプローチを並行検証。--resume <名前> で過去セッションを再開(コード変更後はその旨を伝える。古いツール結果が多いなら要約を注入して新規セッションの方が確実)。

Hooks(決定論的制御)

  • プロンプトによる指示は確率的で失敗率がゼロにならない。業務ルールの保証(本人確認前の返金ブロック、閾値超の取引拒否)には hook によるプログラム的強制を使う。
  • PostToolUse: ツール結果をモデルが読む前に変換(タイムスタンプ形式の正規化など)。ツール呼び出しの送信側をインターセプトしてポリシー違反をブロックし、代替フロー(人間へのエスカレーション)へ誘導するパターンも問われる。

構築手段とフレームワーク

  • 選択肢: Claude Agent SDK(組み込みツール+エージェントループ一式)/ 自作ループ(最大の柔軟性)/ マネージド(Anthropic ホスト。自前ホストとの対比)。
  • エージェント抽象化フレームワークの例: LangGraph、Strands、PydanticAI。マルチステップのワークフロー構築を抽象化する。
  • 共通パターン: tool-use ループ、サブエージェント、メモリ(ファイルベースの永続化)、コンテキストウィンドウ管理。

Domain 6: Prompt and Context Engineering 11.0%

プロンプトエンジニアリング

  • 役割分担: system = 役割・不変のルール・出力形式。user = 個別のタスク・データ。
  • 曖昧な指示より明示的な基準。「保守的に」「高確信のみ報告」のような定性指示は精度を改善しない — 「報告する種類(バグ・セキュリティ)とスキップする種類(スタイル)」をカテゴリで定義する。
  • few-shot は形式の一貫性と曖昧ケース処理の最有力手段。曖昧なシナリオを狙って2〜4例、選択理由も添えると新規パターンへ汎化する。抽出タスクのハルシネーション低減にも効く。
  • 入出力の具体例(2〜3個)は、散文の説明が安定しないときの最良の伝達手段。
  • 入力サニタイズ、反復的改善(テスト駆動、失敗例の共有)、インタビューパターン(実装前に Claude に質問させて考慮漏れを出す)。

コンテキストエンジニアリング

  • lost in the middle: 長い入力の先頭と末尾は確実に処理されるが中間は欠落しやすい。重要な要約は先頭へ、詳細は明示的なセクション見出しで整理。
  • ツール出力はコンテキストに蓄積する前に関連フィールドだけに刈り込む(40フィールドの注文データから必要な5個だけ残す等)。
  • 逐次要約(compaction)のリスク: 数値・日付・金額・顧客の明言した期待値が曖昧化する → 取引ファクト(注文番号・金額・ステータス)は要約の外の「case facts ブロック」として毎プロンプトに保持する。
  • コンテキスト分離: 冗長な探索はサブエージェントに隔離し、要約だけをメインに返す。長セッションでは scratchpad ファイルに知見を書き出して参照(コンテキスト劣化対策)。/compact で圧縮。
  • context drift / bloat の防止 = ツール出力の刈り込み+compaction+サブエージェント分離、と覚える。

出力ハンドリング

  • 構造化出力の最も確実な方法 = tool_use + JSON スキーマ(構文エラーを排除)。ただし意味エラーは防げない(合計が合わない、値のフィールド違い)→ 検証は別途必要。
  • tool_choice: auto(テキストで返す可能性あり)/ any(必ずいずれかのツールを呼ぶ=構造化出力の保証)/ {"type":"tool","name":...}(特定ツールを強制)。
  • スキーマ設計: 元文書にない可能性がある項目は optional / nullable にして捏造を防ぐ。enum には "unclear" や "other"+詳細文字列で拡張性を持たせる。
  • 防御的パース: 自信満々の出力も疑う。検証 → 失敗したら元文書+失敗した抽出+具体的な検証エラーを添えてリトライ(retry-with-error-feedback)。
  • リトライが効くのは形式・構造エラー。情報が元文書に存在しない場合は何度リトライしても無駄。
  • 自己検証フロー: stated_total と calculated_total を両方抽出して突合、conflict_detected ブール等。

Domain 8: Tools and MCPs 10.6%

ツール実装

  • ツール説明(description)がツール選択の主要メカニズム。曖昧・重複した説明は誤ルーティングの根本原因。入力形式・例・エッジケース・「類似ツールとの使い分け境界」を書く。まず説明を改善するのが「最初の一手」(few-shot 追加やルーティング層より先)。
  • 名前は具体的に(get_weather ではなく用途が伝わる名前)。汎用ツールは目的別に分割(analyze_document → extract_data_points / summarize_content)。
  • ツール数が多すぎると選択精度が落ちる(18個より役割に必要な4〜5個)。サブエージェントには役割に必要なツールだけをスコープする。
  • エラーハンドリング: tool_result に is_error: true。構造化エラー(errorCategory: transient/validation/business/permission、isRetryable、人間可読な説明)で回復判断を可能にする。一律の「Operation failed」は NG。
  • アクセス失敗(タイムアウト等)と「0件の正常結果」を区別して返す。
  • client-side(自アプリで実行、承認ゲート可)vs server-side(Anthropic 実行: web search, code execution 等)の区別。破壊的操作は承認パターンで守る。

MCP サーバー開発

  • MCP = ツール・リソース・プロンプトを標準プロトコルで公開するサーバー。複数アプリで再利用・独立保守したい機能は MCP 化が正解(システムプロンプトへのハードコードやデータ貼り付けは誤答)。
  • 通信: stdio(ローカル・同一マシン)/ HTTP・ソケット(リモート)。クライアント(Claude 側)とサーバー(機能提供側)の役割を区別。
  • MCP リソース = コンテンツカタログ(issue 一覧、DB スキーマ、ドキュメント階層)を公開して探索的ツール呼び出しを削減する仕組み。アクションは「ツール」、参照データは「リソース」。
  • スコープ: プロジェクトの .mcp.json(チーム共有・バージョン管理)vs ユーザーの ~/.claude.json(個人・実験用)。認証情報は ${GITHUB_TOKEN} のような環境変数展開でコミットせずに渡す。
  • 接続時にすべての設定済みサーバーのツールが発見され、同時に利用可能になる。標準的な統合(Jira 等)は既存のコミュニティ MCP サーバーを優先し、自作はチーム固有ワークフローに限る。

Domain 7: Security and Safety 8.1%

  • プロンプトインジェクション対策(最頻出): ① untrusted 入力(Web ページ、ユーザー文書)を信頼済み指示から分離 ② 最小権限 — 注入された指示が機微なアクションを起動できないよう guardrail / hook で制御。
    誤答の定番: temperature 変更(無関係)、システムプロンプトでの「お願い」(強制力なし)、より大きいモデルへの変更(指示追従が良い分、より脆弱になりうる)。
  • guardrail の多層化(layering): 入力フィルタ+プロンプト設計+出力検証+hook による強制、を重ねる。単層に頼らない。
  • hooks: 破壊的アクション(削除、閾値超の送金)をコードで確実にブロック。プロンプト指示は確率的なので保証にならない。
  • secure-by-design: 最小権限、identity/access management、認証・認可・機密性・完全性・プライバシー。
  • 秘密情報管理: API キーはコードに書かず環境変数・シークレットマネージャへ。開発/本番でキーを分離、ローテーション、アクセス承認とレベル検証、アクセス監視。
  • データ漏えい防止・PII の扱い(規制順守、ログやメモリに PII を残さない)。jailbreak 防御。

Domain 3: Claude Code 3.1%

  • CLAUDE.md 階層: ユーザー ~/.claude/CLAUDE.md(個人・バージョン管理外)→ プロジェクトルート(チーム共有)→ サブディレクトリ(その配下のみ)。「新メンバーに指示が効かない」→ ユーザーレベルに書いてある、が定番の診断。@import でファイル分割、/memory で読み込み状態を確認。
  • .claude/rules/: YAML frontmatter の paths:(glob)で条件付き読み込み。ディレクトリ横断の規約(**/*.test.tsx)にはサブディレクトリ CLAUDE.md より glob ルールが正解。
  • スラッシュコマンド: プロジェクト .claude/commands/(リポジトリで共有)vs 個人 ~/.claude/commands/。
  • Skills: .claude/skills/<名前>/SKILL.md。frontmatter: context: fork(隔離実行でメイン会話を汚さない)、allowed-tools(ツール制限)、argument-hint(引数の促し)。Skills = オンデマンド、CLAUDE.md = 常時読み込み。
  • plan mode vs 直接実行: 大規模変更・複数の妥当なアプローチ・アーキテクチャ判断 → plan mode(先に探索・設計)。明確なスコープの単発修正 → 直接実行。冗長な探索は Explore サブエージェントへ。
  • ヘッドレス/CI: -p(--print)で非対話実行(これがないと入力待ちでハング)。--output-format json + --json-schema で機械可読な構造化出力。CLAUDE.md でレビュー基準やテスト規約を CI に伝える。
  • セッション管理: --resume、fork_session、/compact、headless/streaming/auto モード。

Domain 4: Eval, Testing, and Debugging 2.6%

  • トレース分析で失敗モードを特定: どのステップ(分解・ツール選択・ツール実行・合成)で壊れたかをログから切り分ける。下流のエージェントを責める前に上流の入力(コーディネータの分解)を見る。
  • 問題の切り分け: 統合レイヤの問題(認証、タイムアウト、パースエラー)か、モデル出力の問題(誤った判断、ハルシネーション)かをまず区別する。
  • 回復戦略の選択: transient エラー → リトライ(指数バックオフ)。validation → 入力修正。business ルール → ユーザーへ説明。permission → エスカレーション。
  • 自己レビューの限界: 生成と同じセッションは自分の判断を疑いにくい → 独立したレビューインスタンスが微妙な問題の検出に優れる。大規模レビューはファイル別パス+横断統合パスに分割(注意の希釈を防ぐ)。
  • 集約精度(97%)はセグメントの劣化を隠す → 文書タイプ別・フィールド別に層化サンプリングで検証。モデルの自己申告confidence は較正が必要(ラベル付き検証セットで閾値を決める)。
